# sshd issues (review, 2026-11-16)

A source read of the userspace sshd (`userspace/sshd/src/{protocol,main,config,wire}.rs`) against
RFC 4253/4254, followed by fixes on branch `userspace-review`. Each item says what was wrong, how it
was confirmed, and what changed. Findings already in progress on branch `security-fixes`
(`docs/archive/SECURITY_AUDIT_2026_11_16.md` there) are listed at the end and were not touched here.

| # | Severity | Issue | Status |
|---|---|---|---|
| S1 | **Critical** | The connection protocol was served before authentication: unauthenticated root `exec` | fixed, reproduced live |
| S2 | High | `packet_length` was unbounded: a client could make sshd buffer gigabytes | fixed |
| S3 | High | A padding length that left no payload panicked the session (slice out of range) | fixed |
| S4 | Medium | A packet with a bad MAC was dropped and the connection kept waiting | fixed |
| S5 | Medium | The version line was unbounded, and bytes after it in the same read were lost | fixed |
| S6 | Medium | Every channel request was answered SUCCESS, so `sftp`/`scp` and `ssh -W` hung | fixed, verified live |
| S7 | Medium | Any channel type was confirmed (`direct-tcpip`, a second `session`) | fixed, verified live |
| S8 | Medium | The client's channel window was ignored | fixed |
| S9 | Low | A non-UTF-8 `exec` command ran as an empty command | fixed |
| S10 | Low | The full `exec` command line was logged | fixed |
| S11 | Low | Bad CLI/config values and unknown keys were silently ignored; `--help` started a server | fixed |
| S12 | Low | `SERVICE_REQUEST` accepted any service name | fixed |

## S1. Unauthenticated command execution (critical)

`handle_message` dispatched on the message number alone. `SSH_MSG_CHANNEL_OPEN` (90) and
`SSH_MSG_CHANNEL_REQUEST` (98) were handled in **every** state. `MessageResult::StartExec` then ran
the command as root, so authentication and key exchange were only a convention the client chose to
follow. The unencrypted read path also went through `handle_message`, so the requests did not even
need a key exchange: a version line followed by two plaintext packets was enough.

**Confirmed** on a QEMU guest (INSTANCE=3, snapshot disk) against the `697f1ca2` build of sshd and
the older binary on the disk image. A raw TCP client sent the version line, `CHANNEL_OPEN session`
and `CHANNEL_REQUEST exec "touch /tmp/<marker>"`, and the marker file appeared, owned by root. The
same probe against the fixed build gets the connection closed and no file.

**Fix.** `transport::message_allowed(phase, msg)` is checked at the top of `handle_message`, and
the bridge loops have their own phase checks. Transport messages that are always legal (DISCONNECT,
IGNORE, UNIMPLEMENTED, DEBUG) pass in any phase. Otherwise each phase admits exactly one message
(KEXINIT, KEX_ECDH_INIT, NEWKEYS, SERVICE_REQUEST, USERAUTH_REQUEST), and only `Authenticated`
admits the connection protocol (80–100). Anything else is a disconnect. A KEXINIT after the
handshake is also a disconnect, with "re-key not supported" in the log; re-keying is M1 in the
audit. Host tests in `transport.rs` check every message number in every phase.

**Exposure.** Every build before this branch, both architectures, every box whose sshd port is
reachable. That includes the cluster boxes on the LAN and anything an image or AMI was made from.

## S2–S5. Transport framing

- **S2.** `packet_length` came off the wire and sized the input buffer before any check. It is now
  capped at `MAX_PACKET_LEN` (256 KiB; RFC 4253 §6.1 requires 35000) before anything is buffered.
- **S3.** `payload = packet[1 .. packet_length - padding_length]` panicked when
  `padding_length + 1 > packet_length`. `transport::payload_len` rejects it.
- **S4.** A MAC mismatch logged and returned "no packet", so the connection waited for data
  that would never verify. It is now `PacketError::BadMac`, and the connection closes.
- **S5.** The version line was read until `\n` with no cap. It is now capped at 255 bytes
  (RFC 4253 §4.2). A client that sends its version line and KEXINIT in one segment, as OpenSSH
  can, used to have the KEXINIT dropped. The rest of the buffer is now parsed.

## S6–S8. Channels

- **S6.** `CHANNEL_REQUEST` sent `CHANNEL_SUCCESS` for any request type with `want_reply`.
  `subsystem sftp` was "accepted" and then nothing answered, so `sftp` and `scp` (which uses
  sftp by default) hung forever. Only `shell`, `exec`, `pty-req`, `env` and `window-change` are
  supported now; anything else gets `CHANNEL_FAILURE`. Verified live: `sftp` printed
  `subsystem request failed on channel 0` in 0.1 s; against the old build it hung until the
  harness timed out.
- **S7.** Every `CHANNEL_OPEN` was confirmed, whatever its type. `ssh -W` and `-L` "succeeded"
  and then hung. A non-`session` type gets `OPEN_UNKNOWN_CHANNEL_TYPE`, and a second channel gets
  `OPEN_RESOURCE_SHORTAGE` (sshd serves one channel per connection). Verified live: `ssh -W`
  prints `stdio forwarding failed` at once.
- **S8.** The client's initial window and `WINDOW_ADJUST` were never read, so sshd could send
  more than the client allowed (RFC 4254 §5.2). `remote_window` is now tracked. Stdout reads are
  sized by `transport::stdout_read_budget`, which offers half the window when `\n` is cooked to
  `\r\n`, since that can double the bytes. The final drain waits for an adjust (`await_window`).

## S9–S12. Smaller items

- **S9.** `exec` with a command that is not UTF-8 ran `/bin/sh -c ""` and reported success. It now
  says why and reports exit status 127.
- **S10.** The log line held the whole command, which can carry secrets passed on a command line.
  It now keeps the first 120 bytes (`wire::log_prefix`, cut on a char boundary).
- **S11.** `--port 22x` silently served on the default, and an unknown flag or config key was
  dropped without a word. These now print a warning on stderr with the default that applies. They
  are deliberately not fatal: on a box whose only remote access is this daemon, refusing to start
  is worse than starting on a default. `--help` printed "unknown argument" and **started a
  server**. It now prints usage and exits.
- **S12.** Any service name was accepted. It must be `ssh-userauth`.

## Verification

- Host: `cargo test -p sshd --lib --no-default-features --target <host>`, 74 passed. Builds:
  aarch64 default, `--no-default-features --features akuma,emergency-paws`,
  `--features builtin-paws`, and `x86_64-unknown-none`.
- Live, QEMU aarch64 guest, OpenSSH client, old and new sshd side by side on one guest:
  - Exit status (`exit 3` gave 3), a 900 KiB and a 4.4 MB exec output byte-exact, an interactive
    `-tt` shell, and a 300 KB stdin echo all behave the same as before.
  - The S1 probe, sftp and `-W` behave as described above.
- Throughput, like for like (the `697f1ca2` sshd against this branch, same guest, six interleaved
  runs each of a 4.4 MB `seq`): 5.3–6.0 s against 5.3–5.7 s, so no regression. The older binary on
  the disk image ran the same output in 3.7–4.6 s. That gap predates this branch and was not
  investigated.

## Not done here

- **On `security-fixes`, not touched here:** C1 (key-exchange secret derived from the KEXINIT
  cookie), C2 (host-key entropy), and M1 (no re-keying, pre-auth slot limits, private key file
  mode). Merging the two branches will conflict in `protocol.rs` around `handle_message`/KEXINIT.
- Re-keying is still unsupported. A client that re-keys (OpenSSH does after 1 GB or 1 hour by
  default) is now disconnected cleanly, with the reason in the log. Before, a mid-session KEXINIT
  was not handled as a re-key, and the session failed in some less obvious way.
- One channel per connection. Multiplexed clients (`ControlMaster`) get `OPEN_RESOURCE_SHORTAGE`
  for the second channel.
