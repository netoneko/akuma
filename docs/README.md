# Akuma OS Documentation

This is the front door for all Akuma documentation. Use the tables below to
find what you need.

## How these docs are organized

```
runbooks/     Action-first. "Do X, expect to see Y." For debugging and building.
reference/    Current-state architecture and invariants. No history.
userspace/    Thin pointers to per-binary docs (kept co-located with source).
archive/      Every historical doc, moved verbatim. Linked from new docs, never rewritten.
```

Authoring conventions for each kind live in that section's own README:
[`runbooks/README.md`](runbooks/README.md) and
[`reference/README.md`](reference/README.md).

## Stability grades

Each reference doc carries a grade based on git churn history (608 commits
across 179 archived docs, Dec 2025 – Jul 2026):

- **A — Stable:** dormant or stabilized 2+ months. Safe to trust.
- **B — Watch:** low/med churn, recent but not chronic. Verify behaviour.
- **C — Active risk:** high churn, touched in Jun/Jul. Expect surprises.

The fire windows were late Feb–Mar 2026 (syscall-gap crisis) and Jun 2026
(memory + signal crisis). April/May were the cool-down tails.

If you see this line it is a different defect and the missing trap frame is itself the finding: [`runbooks/debug-thread-spawn-segv.md`](runbooks/debug-thread-spawn-segv.md) §2h |
| A post-fix `-j4` run shows **zero** faults of the row above and you want to call it fixed | Don't, unless it passed **T733** with the build running. Fault onset tracks build start, not uptime; three instrumented runs wedged at T64–T132 (400 % CPU, `[BKL] stuck`) — all *before* the window where faults appear. Check `grep -ac '\[RELR\] slot'` **and** the last `[T…]` timestamp: [`runbooks/debug-thread-spawn-segv.md`](runbooks/debug-thread-spawn-segv.md) → "Verification is currently blocked by the wedge" |
| A recycled thread slot reports the previous occupant's user entry point / SP | **FIXED 2026-08-06** — `init_thread_slot_context` set `is_user_process = 1` while leaving `user_entry`/`user_sp`/`user_tls` stale, and `get_saved_user_context`'s fallback gated only on that flag. A real latent defect, **not** a demonstrated cause of the row above (the trap-frame branch normally wins during a clone). Regress with `threading::state_transition_guard_tests::a_recycled_slot_does_not_inherit_the_previous_occupants_user_entry` (host, two-sided) |
| A `-j4` build wedges: rustc/cargo processes alive but idle, load 0.00, no faults at wedge time | **Diagnosed 2026-08-06 — downstream of the row above, NOT a scheduler/futex bug.** The instruction aborts kill build children; cargo's jobserver tokens die with them; everyone parks forever on the empty jobserver pipe (`[PIPE-DUMP] bytes=0, writers>0` = kernel exonerated). Fix the row above; do not re-chase futexes |
| Nightly `cargo` dies instantly under HVF with `[Exception] Unknown from EL0: EC=0x0` at a **constant** `ELR`, ~71 syscalls into startup | **FIXED 2026-08-06.** The constant `ELR=0x112ac280` is OpenSSL's `OPENSSL_cpuid_setup` executing `SM3SS1` (FEAT_SM3), which Apple Silicon lacks — a CPU-feature *probe* that expects SIGILL. The kernel's `EC=0x0` arm hard-killed instead of delivering SIGILL, so the probe handler never recovered (TCG `-cpu max` implements the insn, so `HVF=0` avoided it). Fix: deliver SIGILL via `try_deliver_signal` in the `EC=0x0` arm. `EC=0x0` is an undefined instruction, **not** the `CNTP` trap the old note claimed (that would be `EC=0x18`). Nightly cargo now runs, restoring the fingerprint-cache fast path: [`runbooks/selfhost-kernel-build.md`](runbooks/selfhost-kernel-build.md) §6 + [`archive/NIGHTLY_CARGO_HVF_SIGILL.md`](archive/NIGHTLY_CARGO_HVF_SIGILL.md) |

[`runbooks/debug-futex-lost-wakeup.md`](runbooks/debug-futex-lost-wakeup.md) §4a + [`reference/subsystems/scheduler.md`](reference/subsystems/scheduler.md) -> "Park/wake handshake". `-j1` is still the documented recipe until a `-j4` run confirms the fix in-VM |

| `qemu-system-aarch64: Assertion failed: (isv), … hvf.c, line 1883` (QEMU exits 134) | HVF could not decode a guest MMIO access — the kernel dereferenced garbage into the MMIO window. Downstream symptom of the ld-musl class above; a supervisor loop must treat it as a normal outcome and reboot |
